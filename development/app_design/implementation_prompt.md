# Turbodash interface redesign: implementation prompt

This specification incorporates the user's approved decisions from 19 October 2026, preserved in [approved_feedback.json](approved_feedback.json). The optimization edition is the first implementation target. The earlier [interactive review](review_v2/index.html) remains a design study; its sample data are illustrative and it does not reproduce every approved interaction.

---

## Copy-ready prompt

Redesign Turbodash into a professional scientific computing workspace using the requirements below and the approved decisions from `development/app_design/review_v2/decisions.json` or the user's exported feedback. Keep the Dash backend, numerical solver, Python API and existing YAML compatibility. Make all changes, generated artifacts and test outputs inside the Turbodash repository. TurboMoC may be inspected as a read-only reference; do not modify its repository.

The visual direction is Blueprint Workbench for the light theme: a pale inspector, a quiet light results canvas, clear blue actions and restrained emphasis. Offer a complete dark theme as well. The interface should make precise model editing comfortable, preserve the full scientific functionality, and leave generous space for plots and reports.

### Confirmed interface requirements

**Application shell and identity.** Show the logo next to **Turbodash** at the top left. Remove “Studio” from the product name. Use the approved blade-ring vector logo with light and dark variants; use one recognizable silhouette with colors appropriate to each background. Check its legibility at header and favicon sizes. Preserve an accessible Turbodash label. Put **Load YAML** and **Save design** at the top right, using recognizable upload/folder and download/save icons alongside the text. Keep their existing import, validation and export semantics. Place a clearly labelled Light/Dark selector at the far right of the header; follow the operating system until the user explicitly selects a theme; theme changes affect the entire interface, figures, tables, tooltips, dialogs and focus states without rerunning the solver or changing model values.

**Three workspaces.** Retain Meanline, Geometry and Mesh with a clear selected state. Use **Left workspace rail** for placement and wording. Changing workspace changes the view only. Preserve active stage/row, unsaved edits, valid results, mesh state and running optimization state. Use a labelled left workspace rail. The desktop layout should have a resizable, independently scrollable inspector and a larger results area; use a drawer at narrow widths.

**Five numbered, expandable sections.** Start with all sections closed on a fresh app visit or newly loaded design. Opening one section need not close another. Ordinary edits must preserve the user's open sections. Use a short summary beside the title where useful, plus an issue indicator if validation fails. Provide an accessible Collapse all action.

1. **Turbine setup:** turbine type, stage count and loss model. Put the loss-model selector here near the top. Stage count remains an integer; distinguish adding/removing stages from selecting the stage being edited.
2. **Operating point:** working fluid, inlet property pair and its two conditions, exit pressure, mass flow rate and inlet flow angle. Use readable labels and persistent units. Follow the TurboMoC interaction pattern described below.
3. **Shaft speed:** specific/actual speed mode and its corresponding value and units. Resolve global blade velocity ratio placement through **Shaft speed**.
4. **Stage design & geometry:** one stage selector displaying the actual stage names, followed by that stage's aerodynamic controls and blade geometry. Use clearly selected **Stator / Rotor** buttons above the corresponding blade fields. Retain every work-split, reaction, angle, velocity-ratio, radius-ratio and geometry control already supported. Preserve axial/radial applicability. The menu must not grow into a separate large accordion for every stage.
5. **Optimization:** keep the existing Settings / Variables / Constraints controls and their full behavior at the bottom of the editor. Solver state and failure information remain discoverable while the section is collapsed. Preserve asynchronous jobs, session isolation, convergence history and coherent application of successful results. Retain cancellation controls wherever they already exist; adding a new cancellation protocol is outside this visual redesign.

Use one numeric field per row, including optimization lower/initial/upper bound fields in the inspector. Make variable names readable words; a mathematical symbol may follow in parentheses. Keep units visible. Use comfortable vertical spacing rather than squeezing two unrelated variables into one row. Continuous numeric fields must accept arbitrary valid floating-point values, including scientific notation where supported, with `step="any"` and committed/debounced updates. Stage counts, iteration limits and other inherently discrete controls retain integer rules. Physical bounds, finite-value validation and model validation still apply. Never round stored values to match displayed precision or slider steps. Handle blank and partially typed numbers without replacing a valid design with defaults.

Reserve inline space for essential information: invalid input, stale results, active jobs and errors needing action. Put supplementary explanations in tooltips accessible by hover, keyboard focus and touch. Tooltips must not be the only place where a field's name, units or error can be found.

**Find a parameter.** Provide a typeahead search above the parameter sections. As the user types, show matching names with enough context to distinguish stage, stator/rotor and workspace. Index full names, existing aliases, symbols and useful synonyms, including currently collapsed controls. Selecting a result activates its workspace, selects the relevant stage/row, opens every containing disclosure, scrolls the field into view, focuses it and briefly highlights it. Selection must not change the value or trigger a solver calculation. Support arrow-key navigation, Enter, Escape and a clear no-results state. Search is a navigational aid, not a second parameter editor.

**Working fluid and property pair.** Inspect TurboMoC's `src/turbo_moc/app/application.py` and `src/turbo_moc/configuration/fluid_inputs.py` as read-only references. Reuse the interaction principles: a searchable fluid selector with readable names, a property-pair selector with human-readable labels, and full-width input fields whose property names and units match the selected pair. Preserve Turbodash's backend identifiers and supported fluid/property-pair combinations. TurboMoC's current pair-change callback updates labels only: do not copy that behavior in a way that silently reinterprets the numbers. Implement **Convert from valid state, otherwise request both values** as one validated state transition. If preserving state, convert from the last valid thermodynamic state using the existing property backend; commit both new values and the pair together only if the conversion succeeds. Otherwise retain the valid state and require explicit new input. Keep the user's invalid draft visible while showing an actionable validation error and retaining the last successful results.

**Report overview.** Show four compact, consistent metric cards above the detailed reports, populated from one coherent successful calculation:

| Label | Existing source in `results["overall_performance"]` | Display |
| --- | --- | --- |
| Total-to-static efficiency | `efficiency_ts` | Fraction converted to percent for display only |
| Total-to-total efficiency | `efficiency_tt` | Fraction converted to percent for display only |
| Shaft speed | `rotational_speed` | rpm; already reported in rpm by the solver. “Rotational speed” is also accurate; avoid implying radians per second through an unqualified “Angular speed” label. |
| Power | `power_actual` | W below 1,000; kW below 1,000,000; MW thereafter, using magnitude and retaining sign; two decimal places |

Use actual shaft power, not isentropic power or a trend-sweep value. Select power units by absolute magnitude and retain the sign. Promote to the next unit if rounding to two decimals would otherwise display 1,000.00 of the smaller unit: for example, 999.995 W becomes 1.00 kW and 999,995 W becomes 1.00 MW. Formatting changes display only. Use an em dash for unavailable or nonfinite values rather than a fabricated zero or NaN, and mark retained results stale when appropriate. Keep detailed tables for all existing performance metrics. Style tables for both themes with readable headers, right-aligned numeric columns, tabular numerals, subtle row separation, hover/focus states and horizontal scrolling where needed. Retain existing precision, unit meaning, data access and exports. Existing reporting functions already scale and format some columns: avoid double conversion, retain numeric sorting and preserve raw export values. Do not replace full reports with the four cards.

**Plot layout and behavior.** Place the meridional channel and blade-to-blade views side by side on normal desktop widths; stack them on narrow screens. Keep useful zoom, pan, reset and image export tools. Hide only the Plotly logo with the graph configuration `displaylogo=False`. Apply theme colors consistently, preserving physically useful line distinctions and legible units.

Upgrade the meridional channel view to show continuous hub and shroud boundaries, restrained surface shading, readable stator/rotor identity and smooth guide streamlines, following the user's subsequent visual feedback. Derive row and endwall geometry from actual results. Extend the passage upstream and downstream at the inlet/outlet dimensions for visual context; these extensions do not modify mesh or solver geometry. Guide streamlines must remain inside the channel and be identified in hover help as illustrative paths, not a CFD solution. Use orange/blue outlines and matching translucent fills for stator/rotor regions and blade profiles. Support single-stage and multistage axial and radial designs. Connect appropriate row and stage gaps, preserve coordinate conventions and apply global offsets exactly once. Match axial placement with the blade-to-blade view. Preserve physical aspect ratio. Compute the upper extent from all rows and stations so upstream shroud geometry cannot be clipped; set the lower y-axis bound to zero on initial view and autoscale/reset while allowing deliberate manual radial zoom.

Distinguish the meanline channel from an exported/generated mesh. The existing meanline view can show flared hub/shroud surfaces, while the TurboMoC mesh adapter currently uses cylindrical averaged row radii. Do not present one as an exact preview of the other or silently change mesh geometry to make them match. If a mesh/geometry preview uses a different physical surface model, retain that source of truth and expose the distinction in concise hover help.

### Implementation sequence

**1. Audit the current source against the approved choices.** Review the selected app editions and their tests before editing. Current entry modules are `turbodash/apps/app_turbine/app.py`, `app_turbine_experimental/app.py` and `app_turbine_optimization/app.py`; shared resources live in `turbodash/apps/shared/`. Read the optimization `panel.py`, `model.py` and `jobs.py`, shared mesh and TurboGrid components, reporting code and visualization helpers. Record every existing input, result view, import/export action and background task so the redesign loses no functionality. Record the approved decision values and compare the review against those values.

**2. Establish safe model and UI state ownership before changing the stage editor.** The present `stage_data_store` is not a continuously synchronized canonical copy of every live input: some calculations assemble state from mounted controls. Rendering only the selected stage without addressing this can discard edits. Either introduce and test one authoritative model store with explicit, atomic transitions, or keep every stage's inputs mounted and hide inactive editors. Separate model data from UI state such as theme, disclosure state, workspace, search and active stage/row. Prevent callback feedback loops and partial multi-field calculations. Preserve stage names and stable UI identities during load/save, selection and resizing the stage count; current `_assemble_cfg` rebuilding `stage_i` keys needs explicit attention. Do not add incompatible YAML fields simply to support UI identities. Keep the last valid model/result alongside invalid drafts. Verify load/save and optimization result application before styling.

**3. Build tokens, typography and approved identity assets.** Use shared CSS variables for surfaces, text, borders, accents, focus, status and charts. Start the light palette from Blueprint's `#EFF3F8` canvas, `#F8FAFD` light inspector and `#2462D1` primary accent; validate actual foreground/background combinations for readability. Implement **Graphite with restrained blue accents** and **Follow the operating-system preference initially**. Build and review the selected vector logo in both themes. Register shared assets through the existing app asset machinery and retain app-specific assets where appropriate. Use a clear system sans-serif, readable form text and tabular numerals; reserve monospaced text for technical logs.

**4. Assemble the shell, disclosures, scoped editor and search.** Add the header actions, theme selector, workspaces and responsive inspector. Implement the five-section organization, stage-name selector and Stator/Rotor controls using the state foundation. Centralize parameter metadata for labels, units, validation hints, aliases and navigation targets so search cannot drift from the editor. Keep disclosure content mounted unless safe state synchronization has already been proven. Implement keyboard and focus behavior as part of this step.

**5. Improve fluid input and numeric editing.** Apply the TurboMoC-inspired selector and property labels without changing backend enumerations. Implement the approved atomic property-pair transition, supported fluid validation and preservation of invalid drafts. Display continuous numeric fields with at least three decimal places, preserving extra supplied digits and meaningful scientific notation; never round the underlying model or interrupt active typing. Keep discrete counts as whole numbers. Verify floating-point precision, scientific notation, physical constraints and speed-mode units. Resolve slider behavior and global velocity-ratio placement using the selected decisions.

**6. Add metric cards and restyle all reports.** Bind cards and detailed tables to the same successful result revision. Format efficiencies, rpm and adaptive power units; preserve full data precision and all report tabs/exports. Theme existing table components before considering replacements; add dependencies only if existing components cannot meet an approved requirement. Confirm stale, empty, error and running-job states in both themes.

**7. Implement the meridional geometry update and paired view.** Start with `turbodash/visualization/plotly_turbine.py::plot_turbine_meridional_channel` and `plot_turbine_blades`, then inspect `plotly_mesh.py::_meridional_style` and `turbodash/geometry/assembly.py` for shared conventions. The existing meanline plot already starts at zero, but its axial upper bound considers only each stage's final station; fix that clipping case. Prefer lightweight shared channel-coordinate extraction over importing expensive mesh generation into routine meanline updates. Share axial row placement between both figures using `chord_meridional` and the existing gap factor of `1.5 * opening`. For axial rows, hub/shroud radii use `r - H/2` and `r + H/2`; the radial plot instead uses spanwise coordinates `-H/2`, `+H/2` and radial coordinate `r`. Do not apply the axial formula to radial surfaces. Reuse verified assembly/gap conventions where applicable; the existing assembly helper is axial-specific, so radial handling needs its own validated geometry path. Add boundaries, passage extensions, shading and smooth guide streamlines, preserve global alignment, replace hard-coded black axes/white templates with theme-aware styling, and apply `displaylogo=False` consistently to relevant graph configurations.

**8. Integrate optimization, geometry and mesh workflows.** Preserve live meanline updates on committed valid edits; do not add a redundant Calculate action. Optimization and mesh generation remain explicit operations. Exercise running, failure, successful application, any existing cancellation behavior, and stale-mesh scenarios while changing theme, stage and workspace. Keep job and result state coherent and preserve session ownership. Place mesh controls and exports where their scope is clear; changing inspection settings must not look like regenerating the mesh.

**9. Verify behavior and visual quality, then document the result.** Add focused regression coverage for state transitions and geometry, reuse existing solver tests, and exercise the actual Dash application in a browser. Save light/dark, collapsed/expanded, desktop/narrow, single/multistage and error-state screenshots under `development/app_design/`. Report actual tests performed and any optional integrations unavailable in the local environment. Update app documentation and the final decision record. Make a descriptive local commit under the user's existing authorization; do not push or deploy implicitly.

### Acceptance criteria

- A fresh design opens with all five sections closed; sections remain stable while editing. Stage and row selection never lose edits, reset untouched stages, rename imported stages or contaminate another stage's values.
- Load/edit/save/reload preserves every supported model and optimization field and the existing YAML schema. Theme, workspace and search navigation leave the model unchanged. Invalid drafts retain the last successful result and block inappropriate calculations or exports with a useful message.
- Light and dark themes cover every control, chart, table, popup and status. Branding contains no “Studio”. Header actions remain recognizable, labelled and usable at narrow widths.
- Every applicable parameter can be found through names and useful aliases. Search results expose their scope; keyboard selection opens, reveals and focuses the correct field without editing it. Disclosure headers, stage/row selectors and tooltip triggers work without a mouse.
- Floating-point values display at least three decimal places and retain additional supplied digits, including small nonzero tolerances. Formatting must not interrupt active, blank or incomplete edits, trigger calculations, or round values on entry, navigation or save. Stage counts and other inherently discrete controls retain integer rules. Property-pair changes never reinterpret existing values and units; both new inputs commit atomically or remain explicitly invalid.
- The four cards agree with the detailed reports for the same calculation. Power formats correctly on either side of W/kW/MW thresholds, including rounding-boundary promotion, and retains sign. Unavailable/nonfinite results are not displayed as zero. Full tables retain their data and exports.
- The meridional plot shows continuous hub/shroud geometry, inlet/outlet extensions and illustrative guide streamlines for one and multiple stages, axial and radial. No duplicate offset or gap is introduced. A case with a larger upstream shroud remains fully visible. The approved zero-axis behavior survives rerender, resize and Plotly reset/autoscale. The paired blade view remains physically aligned where its coordinate system permits.
- Plotly branding is hidden while useful graph controls remain. Chart and table text is readable in both themes; labels, focus and status have sufficient contrast and do not depend on color alone.
- Existing optimization, per-session isolation, mesh generation/inspection and TurboGrid export behavior passes relevant regression checks. No unapproved redesign is spread to other app editions or any files outside Turbodash.
